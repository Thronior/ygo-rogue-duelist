# Dueling AI

The CPU opponent from Yu-Gi-Oh! Rogue Duelist is a JavaScript AI that plays complete Yu-Gi-Oh! duels. It runs on the Project Ignis (EDOPro) rules engine compiled to WebAssembly, so the card rules are the real engine's, not an approximation. It works in a browser and in Node.js, and it can play either seat, or both.

What to expect:

- **Tuned for 2004–2005 cards.** It was built and tested on the game's pool of about 2,000 cards from that era (Goat-format style decks, Master Rule 1), with special handling for many of them. Other cards still work through the engine, but the AI only uses general judgement for them.
- **Plays fair.** It's written to decide from what its own seat can see. It doesn't look at the opponent's hand or face-down cards.
- **Reproducible.** The same decks and seed always produce the same duel.

There are two ways to use it:

- **Let the AI run the duel** with its bundled engine, for a web game, a Node.js server or a simulator. Start with [Try it](#try-it).
- **Plug it into a duel your project already runs**, such as an EDOPro fork or another ocgcore-based game, server or bot. See [Plugging into an EDOPro-based project](#plugging-into-an-edopro-based-project).

## Try it

From the root of this repository:

```powershell
runtime/ai/node.exe tools/dueling_ai_demo.mjs data/decks/bonz-tier-1.ydk data/decks/espa-roba-tier-1.ydk 1
```

```text
Seed 1: player 0 (data/decks/bonz-tier-1.ydk) wins
Turns: 7, decisions: 122, LP: 8000 / 0
```

The AI plays both sides. Any `.ydk` deck works if all its cards are in `data/cards.json`. [tools/dueling_ai_demo.mjs](../tools/dueling_ai_demo.mjs) is about 50 lines and is the best starting point to copy from. Use any Node.js new enough to run it: it was tested on Node 24, and Node 14 can't load it.

## Files to copy into your project

Everything lives in [`android/web/`](../android/web/). Copy these into one folder in your project, for example `dueling-ai/`, and keep them side by side. They import each other with relative paths.

| File | What it does |
|---|---|
| `duel.js` | **The entry point.** `MobileDuel` runs a duel and decides for whichever player is prompted. |
| `engine.js` | Wraps the rules engine: starts duels, sends responses, reads the board. |
| `smart_policy.js` | Scores the options for each kind of decision. This is where most of the AI's judgement lives. |
| `deck_policy.js` | Card-specific knowledge: when to use particular cards and what to target. |
| `battle-planner.js` | Plans attack order. |
| `field-knowledge.js` | Tracks what the AI's seat has legitimately seen, such as cards revealed earlier. |
| `cpu-ranking.js` | Picks between options that score the same, without randomness. |
| `cpu-card-plans.js` | Small planners for tributes and ritual summons. |
| `custom-card-policy.js`, `dna-surgery-policy.js` | Policies for a few individual cards. |
| `replay-rules.js` | The list of behaviour rules enabled after replay testing. |
| `selection-feedback.js`, `effect-feedback.js` | Track targets and effects from public engine messages. |
| `trap-return-compat.js` | Works around an engine bug with trap monsters. |
| `replays.js`, `replay-version.js` | Records each duel's moves so it can be replayed. |
| `system-strings.js` | The engine's standard prompt text. This file is generated by the build (see below). |
| `cpu-deck-model.js`, `collector-rules.js` | `shuffleCPUDeck`, the seeded deck shuffle. Optional: you can shuffle your own way. |
| `edopro-adapter.js` | Only needed to plug the AI into a duel run by another engine (see below). |
| `vendor/package/` | The rules engine: ocgcore-wasm 0.1.2 with a small fix. Copy the whole folder, and use this copy rather than the npm package, because the build patches it. |
| `engine-data.json` | Engine stats for about 14,700 cards. |
| `scripts.json` | The Lua effect script for each card (about 13,500). |

You also need card details: names, text and stats. This project keeps them in [`data/cards.json`](../data/cards.json).

`system-strings.js` isn't in Git. Running `python/python.exe -B tools/build_android.py --sync-only` creates it from `runtime/config/strings.conf`. If you don't need the engine's prompt text, a file containing only `export const systemStrings={};` works too.

## Use it in your code

```js
import fs from 'node:fs';
import {MobileDuel} from './dueling-ai/duel.js';
import {shuffleCPUDeck} from './dueling-ai/cpu-deck-model.js';

const json = path => JSON.parse(fs.readFileSync(path, 'utf8').replace(/^\uFEFF/, ''));

// 1. Card details for every card that can appear in the duel.
const cards = json('cards.json');

// 2. Load the engine with its card data and scripts.
const duel = await new MobileDuel(cards).init([
  json('dueling-ai/engine-data.json'),
  json('dueling-ai/scripts.json'),
]);

// 3. Start a duel. Decks are lists of card IDs (passcodes), one entry per copy.
//    The engine draws in the order given, so shuffle the Main Decks first.
const seed = 42;
let state = duel.start(
  shuffleCPUDeck(myDeck.main, seed, 0), shuffleCPUDeck(cpuDeck.main, seed, 1),
  8000, 8000,     // starting LP for player 0 and player 1
  5,              // opening hand size
  seed,
  myDeck.extra, cpuDeck.extra,
);

// 4. Each time the engine waits for a decision, ask the AI and send its answer back.
while (!state.finished) {
  state = duel.respond(duel.auto());
}

console.log('Winner:', state.finished.player);   // 0 or 1; any other value is a draw
duel.destroy();
```

**In a browser,** the code is the same, except you load the two JSON files with `fetch` and pass them to `init()` yourself. Serve the files over HTTP; the engine can't load from `file://` pages. `init()` with no argument fetches `engine-data.json` and `scripts.json` relative to the page, not the script.

## Playing against the AI

Every prompt says which player must answer (`duel.pending.player`). Let the AI answer for its seat and your UI answer for yours:

```js
while (!state.finished) {
  const prompt = duel.pending;
  const response = prompt.player === 1 ? duel.auto() : await askThePlayer(prompt);
  state = duel.respond(response);
}
```

For your UI:

- `duel.choices()` gives a labelled list of options for the common prompts: main phase actions, attacks, chains, yes/no, positions, zones and options. Each option has a `label` and a ready-made `response`.
- Card selections (choosing cards, tributes, material sums, counters, types and attributes) aren't in that list. Build those from the fields of `duel.pending`. The game's own UI in `android/web/mobile.js` shows how.
- `duel.respond()` throws if the engine rejects a response, and the duel stays on the same prompt so the player can choose again.

## Plugging into an EDOPro-based project

If your project already runs duels with ocgcore (an EDOPro fork, a duel server, a bot), keep your engine and let the AI answer for one seat. Each time the core asks that seat for a decision, your project sends the AI:

1. every core message since its last decision, as the raw bytes ocgcore produced, including messages addressed to the other player, and
2. the current board, as raw `OCG_DuelQueryLocation` results for both players.

The AI replies with raw response bytes that you pass straight to `OCG_DuelSetResponse`. Under the hood, [`edopro-adapter.js`](../android/web/edopro-adapter.js) feeds what you send to the same AI code the game uses.

Copy the files listed under [Files to copy](#files-to-copy-into-your-project), including `edopro-adapter.js`. Your engine already runs the card effects, so you can leave out `scripts.json`.

### From JavaScript

```js
import {EdoproAI, QUERY_LOCATIONS, QUERY_FLAGS} from './dueling-ai/edopro-adapter.js';

// When the duel starts:
const ai = new EdoproAI({
  cards,                 // card details, as described under "Card details"
  engineData,            // dueling-ai/engine-data.json
  seat: 1,               // the player the AI controls
  deck: {main, extra},   // the AI's own deck
  lp: [8000, 8000],
  seed: 1234,            // any number; fixes how the AI breaks ties
});

// Each time the core asks player 1 for a decision:
const zones = {};
for (const player of [0, 1])
  for (const location of QUERY_LOCATIONS)
    zones[`${player},${location}`] = queryLocationBytes(player, location, QUERY_FLAGS);  // your engine's raw query
const response = ai.decide(messagesSinceLastDecision, zones);  // byte array for OCG_DuelSetResponse
```

- **Message format:** each entry in `messages` is one message from `OCG_DuelGetMessage` without its 4-byte length prefix, so the type byte followed by the body.
- **Start from the beginning:** create the adapter when the duel starts and forward every message from the first one, so the AI can count turns and track Life Points.
- **When to ask:** ask whenever the core prompts the AI's seat, including chain prompts with nothing to activate (the AI answers "pass").
- **Board queries:** `QUERY_FLAGS` is the set of query flags the AI needs: `QUERY_CODE | QUERY_POSITION | QUERY_LEVEL | QUERY_ATTRIBUTE | QUERY_RACE | QUERY_ATTACK | QUERY_DEFENSE | QUERY_EQUIP_CARD | QUERY_COUNTERS | QUERY_STATUS | QUERY_IS_PUBLIC`. Query the deck and Extra Deck as well: the AI uses their sizes.
- **Opponent decisions:** you don't send the other player's responses. The AI learns what happened from the messages that follow.
- **End of duel:** `ai.observe(messages, zones)` forwards messages without asking for a decision, for example the ones that end the duel. It's optional.

### From C++ (or any other language)

[`tools/edopro_ai_bridge.mjs`](../tools/edopro_ai_bridge.mjs) wraps the adapter in a small process that reads one JSON request per line on stdin and writes one JSON reply per line on stdout:

```text
→ {"start":{"seat":1,"deck":{"main":[...],"extra":[...]},"lp":[8000,8000],"seed":1234}}
← {"ok":true}
→ {"decide":{"messages":[[type,...body],...],"zones":{"0,1":[...bytes],"0,2":[...],...}}}
← {"response":[...bytes]}
```

Errors come back as `{"error":"..."}` and the bridge keeps running. It loads `data/cards.json` and `android/web/engine-data.json` by default; use `--cards` and `--engine-data` to point it at your own files.

This is the C++ side, using ocgcore's C API and [nlohmann/json](https://github.com/nlohmann/json). It's adapted from the hook in Rogue Duelist's retired desktop build, which ran this AI inside EDOPro. `AskBridge` sends one line to the bridge's stdin and returns one line from its stdout. How you start and talk to a child process depends on your project (reproc, Boost.Process, QProcess and so on), so that part is left to you.

```cpp
#include <nlohmann/json.hpp>
#include <stdexcept>
#include <string>
#include <vector>
#include "ocgapi.h"
#include "ocgapi_constants.h"

std::string AskBridge(const std::string& line);  // your project: write a line to the bridge, read its reply

constexpr uint32_t AI_QUERY_FLAGS = QUERY_CODE | QUERY_POSITION | QUERY_LEVEL | QUERY_ATTRIBUTE | QUERY_RACE |
	QUERY_ATTACK | QUERY_DEFENSE | QUERY_EQUIP_CARD | QUERY_COUNTERS | QUERY_STATUS | QUERY_IS_PUBLIC;

static bool IsPrompt(uint8_t type) {
	switch(type) {
	case MSG_SELECT_BATTLECMD: case MSG_SELECT_IDLECMD: case MSG_SELECT_EFFECTYN: case MSG_SELECT_YESNO:
	case MSG_SELECT_OPTION: case MSG_SELECT_CARD: case MSG_SELECT_TRIBUTE: case MSG_SELECT_UNSELECT_CARD:
	case MSG_SELECT_CHAIN: case MSG_SELECT_PLACE: case MSG_SELECT_DISFIELD: case MSG_SELECT_POSITION:
	case MSG_SELECT_COUNTER: case MSG_SELECT_SUM: case MSG_SORT_CARD: case MSG_SORT_CHAIN:
	case MSG_ROCK_PAPER_SCISSORS: case MSG_ANNOUNCE_RACE: case MSG_ANNOUNCE_ATTRIB:
	case MSG_ANNOUNCE_CARD: case MSG_ANNOUNCE_NUMBER:
		return true;
	default:
		return false;
	}
}

class DuelingAI {
public:
	// Call when the duel starts, before the first message.
	void Start(uint8_t aiSeat, const std::vector<uint32_t>& main, const std::vector<uint32_t>& extra,
	           uint64_t seed, uint32_t lp0, uint32_t lp1) {
		seat = aiSeat;
		messages.clear();
		Call({{"start", {{"seat", seat}, {"deck", {{"main", main}, {"extra", extra}}}, {"seed", seed}, {"lp", {lp0, lp1}}}}});
	}

	// Call for every message the core produces, in order: the type byte followed by the body.
	// Returns true when the AI answered; its response has already been set.
	bool OnMessage(OCG_Duel duel, const std::vector<uint8_t>& message) {
		messages.push_back(message);
		// Every prompt's first body byte is the player who must answer.
		if(message.size() < 2 || !IsPrompt(message[0]) || message[1] != seat)
			return false;
		nlohmann::json decide = {{"messages", messages}, {"zones", nlohmann::json::object()}};
		messages.clear();
		for(uint8_t player = 0; player < 2; ++player) {
			for(uint32_t location : {LOCATION_DECK, LOCATION_HAND, LOCATION_MZONE, LOCATION_SZONE,
			                         LOCATION_GRAVE, LOCATION_REMOVED, LOCATION_EXTRA}) {
				OCG_QueryInfo info{AI_QUERY_FLAGS, player, location, 0, 0};
				uint32_t length = 0;
				auto* data = static_cast<const uint8_t*>(OCG_DuelQueryLocation(duel, &length, &info));
				decide["zones"][std::to_string(player) + "," + std::to_string(location)] =
					std::vector<uint8_t>(data, data + length);
			}
		}
		auto response = Call({{"decide", decide}}).at("response").get<std::vector<uint8_t>>();
		OCG_DuelSetResponse(duel, response.data(), static_cast<uint32_t>(response.size()));
		return true;
	}

private:
	nlohmann::json Call(const nlohmann::json& request) {
		auto reply = nlohmann::json::parse(AskBridge(request.dump()));
		if(reply.contains("error"))
			throw std::runtime_error(reply["error"].get<std::string>());
		return reply;
	}

	uint8_t seat = 1;
	std::vector<std::vector<uint8_t>> messages;
};
```

Call `OnMessage` wherever your project handles the core's messages one at a time. In EDOPro's single-player mode that's `SingleMode::SinglePlayAnalyze` in `gframe/single_mode.cpp`, where each packet's `message` and `buffer` together make the bytes to forward. When `OnMessage` returns `true`, the prompt is answered, so skip asking the player for it.

### Version compatibility

The adapter reads messages and board queries with the decoders from the bundled ocgcore-wasm 0.1.2. Rogue Duelist's desktop build used it with EDOPro's native core (ocgcore API 11.0). Message layouts change from time to time between ocgcore versions, so if your core is much newer or older, check that the AI's answers are accepted. If the core rejects a response, it sends `MSG_RETRY`.

[android/test_edopro_adapter.mjs](../android/test_edopro_adapter.mjs) plays duels in which the AI only gets what a native host would send. It checks that the adapter makes exactly the same choices as the AI running inside the bundled engine, and replays one duel through the bridge.

## Reference

`duel.start(deck, enemy, lp, enemyLP, draw, seed, extra, enemyExtra, passives, enemyDraw, tagTeams, rules)`

| Argument | Meaning |
|---|---|
| `deck`, `enemy` | Main Deck card IDs for player 0 and player 1. The last ID is drawn first. |
| `lp`, `enemyLP` | Starting Life Points. |
| `draw`, `enemyDraw` | Opening hand sizes (default 5). |
| `seed` | Number used for the engine's randomness, such as coin flips and dice. Player 0 always goes first, so put a deck in that seat to give it the first turn. |
| `extra`, `enemyExtra` | Extra Deck card IDs. |
| `passives` | Optional Lua run at the start of the duel, used to add custom rules. The game also uses a `-- SHADOW_RUN_AI {...}` line here for its own relic and difficulty hints; leave it out. |
| `tagTeams` | Optional tag duel teams. Leave as `null`. |
| `rules` | `2` for Master Rule 2; anything else gives Master Rule 1. |

`start()` and `respond()` return the current state:

```js
{
  lp: [8000, 8000], turn, phase, player,
  pending,      // the prompt waiting for an answer, or null
  finished,     // null until the duel ends, then {player, reason}
  players: [    // one entry per player
    {monsters, spells, hand, grave, banished, deck, extra, deckTop},
  ],
}
```

Other useful methods and fields:

| Method / field | Purpose |
|---|---|
| `duel.auto()` | The AI's response to the current prompt. |
| `duel.respond(response)` | Send any response (from the AI or a player) and run the duel to the next prompt. |
| `duel.choices()` | Labelled options for the current prompt. |
| `duel.query(player, location)` | Cards in one location. Locations are exported from `duel.js` as `L` (for example `L.HAND`, `L.MZONE`). |
| `duel.logs` | Recent events in plain English, newest first, worded from player 0's side ("You summon…"). |
| `duel.onMessage = m => …` | See every raw engine message as it happens. If you replace it, call the original too: the AI learns from these messages. |
| `duel.replayRecord` | The starting arguments and every response, which is enough to replay the duel. |
| `duel.destroy()` | Free the engine's memory. Call it when a duel ends; the same `MobileDuel` can then `start()` another. |

### Card details

The `cards` list passed to `new MobileDuel(cards)` needs an entry for every card in either deck. Entries look like this (taken from `data/cards.json`):

```json
{
  "id": 86988864,
  "name": "3-Hump Lacooda",
  "desc": "If there are 3 face-up \"3-Hump Lacooda\" ...",
  "type": "Effect Monster",
  "race": "Beast",
  "attribute": "EARTH",
  "level": 3,
  "atk": 500,
  "defense": 1500,
  "data": {"code": 86988864, "type": 33, "level": 3, "attribute": 1, "race": "16384", "attack": 500, "defense": 1500},
  "strings": ["Draw", "", "", "", "", "", "", "", "", "", "", "", "", "", "", ""]
}
```

The AI recognises many cards by their **official English name** and reads their text, so use the official names. `strings` holds the card's effect descriptions, which are shown when the engine asks which effect to use. A card missing from the list still works in the engine, but the AI only sees it as "Card 12345678".

## Good to know

- **Shuffle the decks yourself.** The engine doesn't shuffle at the start, so an unshuffled deck always draws the same opening hand.
- **Replays stay local.** Every duel is recorded in `duel.replayRecord`. In a browser, `replays.js` also keeps the last 100 duels in IndexedDB (`ygo-duel-replays`). Nothing is uploaded unless your code calls `uploadReplays()`. Don't call it: it would send replays to this game's server.
- **Speed.** A full AI-vs-AI duel usually takes a few seconds or less in Node, which makes it practical for simulations. [tools/simulate_deck_matchups.mjs](../tools/simulate_deck_matchups.mjs) runs batches of AI duels and writes win rates and replays.
- **Newer card types.** The bundled engine predates Link and Pendulum cards, and the AI has no specific knowledge of them.

## How it decides

1. When the engine asks for a decision, `duel.js` (`auto()` → `chooseDecision()`) handles it according to the kind of prompt: summon or set, attack, chain, choose targets, pay a cost, pick a zone, and so on.
2. `smart_policy.js` gives every legal option a score, based on board value, threats, Life Points and lethal damage. `deck_policy.js` adds card-specific knowledge on top.
3. Planners handle the parts that need looking ahead: attack order (`battle-planner.js`), tributes and rituals (`cpu-card-plans.js`).
4. `cpu-ranking.js` breaks ties deterministically, so the same position always gets the same answer.

The decision principles were adapted from WindBot's `DefaultExecutor` and a "Classic 2004" WindBot executor; see [data/ai-source](../data/ai-source/). The AI is tested with the `android/test_*.mjs` scripts, for example `android/test_lethal_priority.mjs` and `android/test_cpu_parity.mjs`.
